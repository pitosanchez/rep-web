# Does a citable, ZIP-level disease-burden data source exist for the Bronx?

**Research date:** 2026-08-31
**Scope:** kidney/renal disease burden, or a defensible general disease-burden proxy, at ZIP/ZCTA granularity for the Bronx (NYC)

## Executive summary

**Partially yes, with an important caveat.** CDC PLACES is a real, peer‑reviewed, small‑area‑estimation dataset that publishes ~40 chronic‑disease and health measures at ZCTA (ZIP Code Tabulation Area) granularity nationwide, including for all Bronx ZCTAs — this is a legitimate, citable, ZIP‑level general disease‑burden source and is a large upgrade over the current `weight_tot` proxy. However, **Chronic Kidney Disease specifically was removed from PLACES starting with the 2024 data release** (last available: the **2023 release**, modeled on 2021 BRFSS data, current through 2021). So a kidney‑specific ZCTA estimate exists but is now several years stale and no longer being updated; a currently‑maintained general disease‑burden proxy (diabetes, obesity, high blood pressure, coronary heart disease — all strong renal‑risk correlates) is available and current through the latest PLACES release. No other candidate source (CDC CKD Fact Sheet, NYC DOHMH Community Health Profiles, USRDS) publishes at ZIP‑level granularity at all — see table below. The recommendation is to use **CDC PLACES ZCTA data**, either the archived 2023‑release CKD measure (labeled as 2021 vintage, discontinued) or a current renal‑risk‑factor composite (diabetes + obesity + hypertension, all live in the latest release), joined to Bronx ZIPs via a ZCTA‑to‑ZIP crosswalk.

## Kidney/renal-specific vs. general disease-burden proxy — the crux finding

This was the single fact this research needed to nail down, and it required going past marketing copy into the release history:

1. **CDC PLACES does publish ~40 chronic-disease/health measures at ZCTA level**, using a peer-reviewed multilevel regression and poststratification (MRP) small-area-estimation method that blends BRFSS survey responses with ACS demographic/socioeconomic covariates and Census population data. This is confirmed directly from CDC's own peer-reviewed journal (*Preventing Chronic Disease*, a CDC-published journal) article using PLACES ZCTA data: Benavidez et al. 2024, https://doi.org/10.5888/pcd21.230267.

2. **Chronic Kidney Disease *was* one of those ~40 measures**, published at ZCTA level, defined as self-reported "ever told by a health professional you have kidney disease" from BRFSS, with a national ZCTA-level prevalence distribution reported in the Benavidez et al. paper as: bottom quartile ZCTAs ≤2.7% prevalence, middle 50% >2.7–<3.5%, top quartile ≥3.5% (2020-release data, from 2019 BRFSS). The current-generation ArcGIS Hub layer "PLACES: Chronic kidney disease" still exists as a public map product: https://hub.arcgis.com/maps/cdcarcgis::places-chronic-kidney-disease/about.

3. **CKD was discontinued as a PLACES measure starting with the August 2024 data release.** Multiple independent sources describe the August 2024 PLACES update explicitly: "two measures — chronic kidney disease and core preventive services use for adults aged 65 and older — were discontinued" (2024 release: 40 measures total, none of them CKD). The last release that included CKD is the **2023 release**, which used **2021 BRFSS data**. This means:
   - A named, citable ZCTA-level CKD estimate for every Bronx ZIP **does exist** (2023 PLACES release, 2021 BRFSS vintage) and can be downloaded today from data.cdc.gov's archived release: https://data.cdc.gov/500-Cities-Places/PLACES-ZCTA-Data-GIS-Friendly-Format-2023-release/c7b2-4ecy
   - It is **frozen at 2021** and not being refreshed under CDC's current PLACES program design (as of the 2025 release, per the CRAN `CDCPLACES` package changelog and CDC's own release notes).
   - Likely reason (not directly confirmed on a CDC page during this research, inferred from general PLACES practice): BRFSS's CKD question sits in a state-optional module rather than the core questionnaire, and CDC's PLACES team periodically drops measures whose underlying BRFSS module rotation no longer provides sufficient multi-state coverage to support the MRP model. This should be treated as informed inference, not confirmed CDC-stated rationale — flag if precision on "why" matters later.

4. **General disease-burden proxies remain fully current in PLACES.** Diabetes, obesity, high blood pressure, and coronary heart disease/CHD — all well-established renal-risk correlates — are present in every PLACES release including the current 2025 release, at the same ZCTA granularity, with the same MRP methodology. These are genuinely live, continuously updated, and defensible as a kidney-disease-risk proxy if the team does not want to rely on the frozen 2021 CKD number.

**Bottom line on the crux question:** CDC PLACES CKD-at-ZCTA data is real and was directly confirmed to exist (not assumed) — but it is a discontinued, 2021-vintage measure, not a live one. A general disease-burden proxy built from PLACES' still-live measures (diabetes/obesity/hypertension) is the more defensible **current** ZIP-level renal-risk signal.

## Recommendation for `where-we-live-site/app/api/geo/bronx-zips/route.ts`

### What `weight_tot` currently is

Reading the route handler directly: `weight_tot` comes from `rep-data/data/geo/bronx_zip_to_tracts.json`, which — per `docs/PLATFORM_BUILD_SUMMARY.md`'s own Data Sources list — is built from the **HUD USPS ZIP-to-Census-Tract crosswalk**. It is a **geographic allocation weight** (the share of a ZIP's residential/total address volume that falls inside a given census tract), not a health measure of any kind. In the current code it flows straight into `properties.weight_tot` on each GeoJSON feature and is consumed by the "Disease Burden" map layer's color scale (per `mapLayers.config.ts`, itself labeled `"Approximate — not real prevalence data"`) and, downstream, into the WWLI formula (`WWLI = weight_tot × 100 × 0.60 + weight_res × 100 × 0.40`). It has no epidemiological content whatsoever — it is purely a tract-allocation share being reused as if it were a disease-prevalence value.

### Recommended replacement

Use **CDC PLACES ZCTA-level data**, joined to the 26 Bronx ZIPs:

- **Option A (kidney-specific, but frozen):** Pull the CKD measure from the archived **2023 PLACES release** (`PLACES: ZCTA Data (GIS Friendly Format), 2023 release`, https://data.cdc.gov/500-Cities-Places/PLACES-ZCTA-Data-GIS-Friendly-Format-2023-release/c7b2-4ecy). Filter to `MeasureId = KIDNEY` (or the "Chronic Kidney Disease" short name in the data dictionary — confirm exact field name against https://data.cdc.gov/500-Cities-Places/PLACES-and-500-Cities-Data-Dictionary/m35w-spkz before implementing) and Bronx ZCTAs. Must be labeled in-product as "CDC PLACES, 2021 data — kidney disease measure discontinued by CDC after this release."
- **Option B (general proxy, current):** Pull **Diabetes**, **Obesity**, and **High Blood Pressure** measures from the current (2025) PLACES ZCTA release (`PLACES: Local Data for Better Health, ZCTA Data, 2025 release`, https://data.cdc.gov/500-Cities-Places/PLACES-Local-Data-for-Better-Health-ZCTA-Data-2025/qnzd-25i4) and combine into a composite renal-risk-factor score. This stays current with future PLACES releases and is defensible as a "disease-burden proxy" framing (which is exactly how the current layer is already labeled) rather than an actual CKD number.
- A hybrid is reasonable: ship Option B as the primary, continuously-refreshable "Disease Burden" layer value, and surface Option A's frozen CKD figure as a supplementary stat on the Neighborhood Profile page with an explicit "as of 2021, no longer updated" caption — similar to how the CDC CKD Fact Sheet stats are already handled as narrative context rather than a live map layer.

### Transformation / join needed

1. **ZCTA ≠ ZIP.** ZCTAs are Census Bureau's polygon approximation of USPS ZIP code service areas, built from census blocks, and do not perfectly match USPS ZIP boundaries (USPS ZIPs are delivery routes, not areas; some ZIPs have no residential population and thus no corresponding ZCTA; ZCTA and ZIP codes can diverge in boundary and even in which 5-digit code is used). For the 26 Bronx ZIP codes already in `BRONX_ZIP_COORDINATES`, the majority should have a same-numbered ZCTA (this is the common case for populated urban ZIPs), but this must be verified ZIP-by-ZIP rather than assumed — a formal crosswalk (e.g., HUD USPS ZIP-ZCTA crosswalk, or the Census Bureau's ZCTA relationship files) should be used to confirm/repair the mapping and flag any Bronx ZIP with no direct ZCTA match (P.O.-box-only or non-residential ZIPs like `10499` in the current coordinate table are the likely edge cases).
2. **Suppression / small-population ZCTAs.** PLACES ZCTA estimates are only published for ZCTAs with population ≥ 50 (per Benavidez et al. and the PLACES methodology); all Bronx ZCTAs comfortably clear this, so suppression should not be an issue in practice, but the join logic should still handle a missing ZCTA gracefully (fall back to borough/county-level CDC KDSS estimate or omit the layer for that ZIP, rather than silently defaulting to 0).
3. **Margin of error.** Every PLACES estimate ships with a 95% CI (2.5th/97.5th percentile of a 1,000-sample Monte Carlo draw from the MRP model) — the CI width should be surfaced in the UI (e.g., tooltip) rather than presenting the point estimate as ground truth, consistent with the platform's stated "transparent limits" design principle.
4. **Shape needed:** the join should replace the current `{ weight_res, weight_tot }` pair per ZIP with something like `{ zcta, measure_id: 'KIDNEY' | 'DIABETES' | ..., data_value: <percent>, low_confidence_limit, high_confidence_limit, year, release }`, keyed by ZIP and merged into the existing `zipMap` construction in `route.ts` (replacing or supplementing `data.weight_tot` at the point it's assigned into `properties`).
5. **Year/vintage labeling is mandatory** given the CKD discontinuation finding above — any UI consuming this must state the data year (2021 for CKD; 2022/whatever is current for diabetes/obesity in the live release) so it isn't presented as real-time.
